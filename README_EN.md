## About

`orelia-core` is the main plugin (Paper 1.21.x / Java 21) of the Minecraft RPG plugin suite **Orelia**. The former 3-repo split — orelia-core (combat/player/status foundation), orelia-world (content layer: quest, ...), and orelia-extra (social/economy layer: party, ...) — has been merged into this single plugin; this one repo now provides every feature. [orelia-world](https://github.com/orelia-mc/orelia-world) and [orelia-extra](https://github.com/orelia-mc/orelia-extra) have been archived as part of this merge - all further development happens here.

Orelia is split into the following plugins:

- **orelia-core** (this repo) — Core, Item, Skill, Job, Status, Accessory, Relic, Monster, Boss, Effect, Economy, GUI, Gathering, Region, Town, Database, API, Util (formerly orelia-core), Quest, NPC, Dialogue, Story, Dungeon, CutScene, Event, PlayerInfo (formerly orelia-world), Party, Friend, Guild, Chat, Trade, Mail, Auction, Housing, Pet, Mount, Ranking, Achievement (formerly orelia-extra)
- [orelia-debug](https://github.com/orelia-mc/orelia-debug) — admin-only testplay/debug tooling for orelia-core (remains a separate plugin)
- [orelia-serverutil](https://github.com/orelia-mc/orelia-serverutil) — gameplay-independent server operations/UX plugin (hub transfer, scoreboard/tab-list API, join messages, ...)

The former orelia-world/orelia-extra `rpg.world.api`/`rpg.extra.api` interfaces still exist as internal module-boundary facades and are still published via `ServicesManager` — `orelia-debug` depends on them at runtime. Modules within this repo, however, no longer need to worry about "is the other plugin loaded yet" - the whole suite boots as one plugin in a single deterministic order.

## Setup

```bash
./gradlew build
```

Produces `build/libs/orelia-core-1.0.0.jar`. Requires network access to `repo.papermc.io` (Paper API) and `jitpack.io` (Vault API).

## Structure

- Public API — a genuinely separate plugin (e.g. orelia-debug) integrates through `rpg.api`/`rpg.world.api`/`rpg.extra.api`, published via Bukkit's `ServicesManager` — never through this plugin's internal module classes. See `rpg.api.OreliaApi` and the narrower `StatusApi`/`JobApi`/`ItemApi`/`AccessoryApi`/`SkillApi`/`GuiApi`/`EffectApi`/`CombatApi`/`RelicApi`/`TownApi`/`EconomyApi`/`DebugApi` interfaces, plus `rpg.world.api.QuestApi`/`WorldDebugApi` and `rpg.extra.api.GuildApi`/`PartyApi`/`AchievementApi`/`ExtraDebugApi`.
- Config — every module reads its own file under `src/main/resources/` (`items.yml`, `skills.yml`, `jobs.yml`, `accessories.yml`, `relics.yml`, `monsters.yml`, `bosses.yml`, `effects.yml`, `gui.yml`, `crafting.yml`, `gathering.yml`, `fishing.yml`, `messages.yml`, `config.yml`). Reload all of them with `/oladmin reload`. Every file is tracked by a top-of-file `config-version`; newly added keys (including ones nested inside a section you already have) are automatically spliced into an existing file at the correct position on next startup (`rpg.core.config.ConfigMigrator`). Bump a file's `config-version` whenever you add a new top-level section or key.
- NPC / Nether Star compatibility across the 3-plugin merge — a `NamespacedKey`'s namespace comes from the owning plugin's name, so the merge moved the `npc_id` (NPC entities) and `player_info_item` (the player-info Nether Star) tags from `oreliaworld:` to `oreliacore:`. NPCs placed and stars handed out before the merge still carry the old namespace, so both key holders read the legacy key as a fallback (`rpg.npc.service.NpcKeys`, `rpg.world.playerinfo.service.PlayerInfoItemKeys`). Without it, existing NPCs would go inert *and* get duplicated by `/oladmin npc spawnall`, and existing Nether Stars would stop opening the menu, lose their drop protection, and be pushed out of the hotbar on the next join (into the inventory, or onto the ground if it's full) to make room for a freshly issued one. NPCs are re-stamped under the current namespace as they're read, so each migrates exactly once. Both fallbacks are removable once no pre-merge world or item is in use.
- Config migration for the 3-plugin merge — any `*.yml` you had customized under `plugins/OreliaWorld/` or `plugins/OreliaExtra/` before the merge (`quests.yml`, `npc.yml`, `dungeons.yml`, `achievements.yml`, ...) is copied into `plugins/OreliaCore/` automatically on the first startup after the merge (`rpg.core.config.LegacyDataFolderMigrator`); a file already present in the target is never overwritten. `config.yml` and `messages.yml` are the two exceptions — they were content-*merged* rather than moved, so copying a former plugin's version over this one's would drop every core setting; their new sections are spliced into your existing file by `ConfigMigrator` instead. The database needs no migration at all: orelia-world/orelia-extra always shared orelia-core's own `DatabaseManager`.
- Relics (rollable accessories) — unlike `accessories.yml`'s fully static items, a relic is generated on a dungeon boss kill (`rpg.api.RelicApi#generateRelic`, called from orelia-world) with a random part and one random main stat rolled from that part's `relics.yml` pool. Accessory slots expanded from 4 to 6 (charm/ring/necklace/wing/earring/belt). A relic already rolls `initial-substat-count-min`/`max` (3-4 by default) of its up to-4 substats at generation instead of starting blank, and grows via `/ol relic upgrade` (tab-completed) every 3 levels (max 15, 5 upgrades total) — up until all 4 lines are filled, the player freely picks between adding a new one or growing an existing one each time, then only growing once full (only the magnitude, from `relics.yml`'s `substat-upgrade-min`/`max`, is randomized), a deliberate departure from a pure-RNG artifact system. Wearing 2+ relics from the same source dungeon grants that dungeon's set bonus automatically (`relics.yml`'s `dungeon-set-bonuses`). Separately, `relics.yml`'s `shop-relics:` section defines fixed, already-max-level (but deliberately weaker) relics NPC shops can sell via a `RELIC` shop-entry kind (`npc.yml` shop-stock), and an NPC can open the upgrade GUI directly too (`npc.yml`'s `type: RELIC_UPGRADE`, `rpg.api.RelicApi#openUpgradeGui`).
- Boss bars — spawning a boss shows a vanilla boss bar (HP progress) to any player within 7 blocks, reading the same scaled HP the nametag health bar already uses so the numbers always agree.
- A monster's nametag shows its level next to its name whenever it was spawned with a `targetLevel` from a spawn point (blank for an unleveled one). A player's death message when killed by a monster is also replaced with a dedicated one (`messages.yml`'s `monster.death-message`) so the nametag's HP-bar decoration doesn't leak into it - this covers melee hits, ranged skills (an arrow it fired), and damager-less monster/boss ability attacks (AOE_SLAM, FIREBALL_BARRAGE) alike.
- Arrows fired by a bow skill (パワーショット/マルチショット) can't be picked up and despawn automatically a short time after landing (`config.yml`'s `skill.arrow-despawn-ticks`, 5 seconds by default).
- Versioning — every push to `main` (i.e. every merged PR) auto-bumps `build.gradle.kts`'s `version` by PATCH and tags the commit, via `.github/workflows/version-bump.yml`. Label a PR `bump:minor` for a breaking/compatibility change, or `bump:major` for a large rework, before merging.
- Monster strength — `/oladmin spawnpoint add <monsterId> <intervalSeconds> <maxAlive> <targetLevel>` requires a target level for every spawn point (`monsters.yml` has no level concept of its own - hp/attack-power/defense are template values, and the actual level always comes from the spawn point), scaling that spawned monster's stats using the factors in `config.yml: monster-level-scaling` and showing on its nametag. Spawn points registered before this rule stay level-less until re-registered. Dungeon-spawned monsters/bosses always get a level too (the chosen difficulty), and the GM-only `/oladmin spawn <monsterId> [targetLevel]` one-off spawn still leaves it optional.
- Crafting — `/ol craft` opens the recipe list defined in `crafting.yml`; consuming the listed materials crafts one weapon.
- Debug mode — a per-player admin-toggleable flag (`rpg.api.DebugApi#isDebugMode`/`setDebugMode`, flipped via `orelia-debug`'s `/oladmin debugmode`). While enabled, it bypasses a weapon's job/level requirement, a skill's weapon-type-match/socketed/learned/cooldown/SP-cost checks, and the fishing rod's job requirement entirely (growth gates like the weapon level-up cap or skill-point costs are out of scope). In-memory only - resets on rejoin.
- Fisherman job — like every other job's weapon-type restriction, a fishing rod can only be used while the player's current job is Fisherman (`rpg.gathering.listener.FishingListener`; a vanilla fishing rod carries no `items.yml` weapon data, so this is enforced via `PlayerFishEvent` instead of `WeaponRequirementService`). Fisherman levels independently the same way miner/woodcutter/farmer do (visible via `/ol gathering`), and the bobber's wait time (`fishing.yml: catch-time`) shrinks a little with each level. Catchable items are defined as weighted tables under `fishing.yml: towns`, keyed by whichever matches first: the WorldGuard region ID at the bobber's location (most specific - when a child and a parent region overlap, the child's ID always wins over its parent's), then the Bukkit world name the player is fishing in, then `default`. Adding an area or changing its items only needs editing `fishing.yml` and running `/oladmin reload` - no code change required.
- Mage job and the magic wand — the same idea as HATCHET (woodcutter) and AXE (warrior) sharing axe materials while staying fully separate categories: `WeaponType.WAND` shares the farmer's `HOE` hoe materials but is a fully separate category, and only a Mage may wield it (`items.yml`'s `magic_wand`). The wand has no generic skill sockets (`skill-slot-count: 0`) — instead it has three fixed actions: right-click fires a snowball-based ice bolt that damages whatever it hits (low SP cost and cooldown, the wand's rapid-fire option), left-click erupts Evoker Fangs in a radius-5 AOE centered on the caster, and **swapping the wand into the off-hand** (F by default) opens a magic circle at the caster's feet firing 3 staggered volleys of lasers, a second apart, outward in 8 evenly spaced horizontal directions. None of them can hit the caster. Lasers do not pass through walls (a beam reaching an impassable block stops there), and each volley tracks hits independently, so an enemy caught by several overlapping beams in the same volley still only takes damage once, while one that stays in place across all 3 volleys takes damage up to 3 times. The circle and every volley are anchored to the position where the cast started, so the effect stays put if the caster walks away. A failed cooldown/SP check still lets the hand swap itself go through, so the wand can never get stuck in the off-hand. All three abilities compute damage from the weapon's base attack power and the caster's ATK%, then resolve DEF/crit/elemental weakness through the same path as normal melee damage (`rpg.monster.listener.CombatDamageListener`). The summoned Evoker Fangs are purely visual - their native attack never applies. `MagicWandAbilityListener` manages SP cost and cooldowns for both abilities itself. Because the wand shares a material with hoes, `rpg.gathering.listener.FarmingListener`'s sneak-harvest check also resolves weapon identity rather than just the item's `Material`, so holding the wand never triggers the farmer's bulk-harvest sweep. For the same reason, right-clicking with the wand is suppressed from falling through to vanilla tilling in either hand, off-hand included.
- Town detection / WorldGuard integration (`rpg.region` / `rpg.town`) — when WorldGuard is installed (soft dependency, `plugin.yml: softdepend`, reflection-only with no compile-time dependency), any WorldGuard region ID listed in `config.yml: town-detection.town-regions` counts as "a town". A single town spread across disjoint areas needs one WorldGuard region per area, with all of their IDs listed (WorldGuard region IDs are unique per world, so one ID can't cover two separate shapes). Town detection is used to stop Orelia's own monster spawns (spawn points, `/oladmin spawn`) from happening inside a town, and is published to orelia-world/orelia-extra as `rpg.api.TownApi#isInTown`. Without WorldGuard installed, detection is simply disabled and existing behavior is unaffected.
- Gathering regen vs. player builds (`rpg.gathering`) — natural gathering nodes grow back after the cooldown in `gathering.yml`, but gathering is switched off entirely inside any WorldGuard region listed in `gathering.yml: regen-exclusion.regions`: no regen, no gathering XP, no min-level gate, so a town's decorative trees can't be farmed for woodcutting levels. Because the rule keys off *where* a block is rather than *how it got there*, it covers naturally-grown trees left standing inside a build and WorldEdit/schematic pastes (which never fire `BlockPlaceEvent`) alike; an outdoor player base is protected the same way by drawing a region around it. This is a separate list from town detection (`config.yml: town-detection`) — a forest you don't want regenerating isn't necessarily a town. As a WorldGuard-independent backstop, a restore also only runs while the coordinate still holds the waiting block this system put there (or air): if somebody has since built something else on that spot, the task is dropped rather than overwriting their build. `/oladmin gathering resetregen confirm` clears the pending restore queue. Changing the excluded areas themselves only needs a `gathering.yml` edit plus `/oladmin reload` — already-queued tasks are re-checked at restore time.
- Status GUI (`/ol status`) — split into 3 items (base: HP/SP/ATK/DEF/speed/SP recovery, plus current attack power factoring in the held weapon; crit: crit rate/crit damage; elemental damage: the 6 elements) instead of one cramped lore, with Japanese labels and the viewer's own skin on the head icon. Also shows money and the 6 accessory/relic equip slots (charm/ring/necklace/wing/earring/belt) on the same screen. Equipping/unequipping happens by clicking those slots directly (an empty slot is a red stained-glass placeholder naming the part, and an item of the wrong part is refused). The 6 slots sit in the screen's middle row, which is 9 wide and doesn't split evenly into 6 - an info icon fills the dead-center slot instead, so 3 equip slots sit symmetrically on either side. Equipment lives in a virtual slot set persisted to the database, independent of the player's real inventory, so it survives relog and server restarts.
- Skill GUI (`/ol skill`) — identifies and sockets skills onto a weapon in **any of the player's leftmost 3 hotbar slots**, not main hand (opening this screen from the Nether Star player-info menu requires holding the Nether Star itself in the main hand, so main hand isn't the weapon at that point). Nothing stops a weapon from being moved out of those slots - the design just expects the player to keep one there. Opening the screen auto-selects the first slot that actually holds a weapon; the preview icon in the top-left corner (a clone of the active weapon) has prev/next arrows on either side to flip between the other slots (a purpose-built 3-slot nav rather than `GuiPaginator`, which is built for paging a variable-length list, not flipping between 3 fixed hotbar slots). Right-click to socket, **shift+right-click to unsocket**. A socketed skill's lore shows which socket slot it occupies, and the header explains the cast keys. Skill sockets per weapon come from `items.yml`'s `skill-slot-count` (2 max today). For SWORD/AXE/PICKAXE/HATCHET, socket 1 casts on right-click and socket 2 on the swap-hands key (F by default, cancelling vanilla's hand swap). For BOW (bow/crossbow), SPEAR (trident), and HOE - each of which has its own right-click action (draw, throw, till) that must keep working normally - right-click never casts a skill; socket 1 casts on plain F instead, and socket 2 on sneak+F. Cast feedback (success, on cooldown, not enough SP, etc.) appears on the action bar (next to the HP/SP/ATK readout) instead of chat.
- Swinging a ranged weapon (bow/crossbow) in melee now deals bare-hand damage instead of that item's ranged attack power. An elemental bow's weakness bonus (×1.5) now applies to an actual shot, not just a melee swing with it.
- A melee skill's knockback (dash/cone/AOE) no longer pushes other players when the world's PvP setting is off (monsters are unaffected).
- Vanilla armor is banned - defense comes entirely from the DEF stat (this prevents vanilla armor points/toughness from mitigating damage a second time on top of DEF). The right-click-to-equip gesture itself is cancelled outright (`rpg.status.listener.ArmorBanListener#onInteract`), and any armor that lands in an armor slot through another route (GUI click, drag, dispenser, ...) is immediately taken back off and returned to your inventory. Elytra and non-defensive head items (pumpkins, mob heads, ...) are exempt, since they contribute no defense value. The bow/crossbow infinite-ammo mechanic takes advantage of the now-permanently-free leggings slot: the seed arrow carries a `minecraft:equippable` component and is worn there directly (vanilla's own ammo search scans all 41 inventory slots, armor included, so this satisfies the "has ammo" check) - guaranteed available since armor can never occupy it. That arrow's own `item_model` is overridden to a barrier block, named "No Slot" (its worn appearance stays invisible), and it can't be clicked out of the slot in the inventory screen.
- GUI framework (`rpg.gui.framework`) — money-moving/irreversible actions (e.g. an NPC shop purchase) now go through `ConfirmGuiScreen`, a separate "are you sure?" screen interposed before the action runs. Laying a list out across pages is now shared logic (`GuiPaginator`/`GuiPageLayout`); screens in orelia-world/orelia-extra that currently drop items past a fixed capacity or write out of bounds are planned to move onto this over time. Clicking a button now plays `block.bamboo_wood_button.click_on` by default (lighter actions like page navigation use `ui.button.click` instead). `MessageManager#sendWithSound` lets a caller opt a specific success/failure message into a sound cue without applying one to every message.
- Exponential character growth (`config.yml: status.growth` / `stat-scaling.growth-rate`) — HP/SP/ATK/DEF now grow as `scaled = base * growthRate^(level-1)`, sharing the same rates as monster level scaling (`stat-scaling.growth-rate.HP/ATK/DEF`) so a monster and a player at the same level grow at the same rate. SPD keeps the old flat `base + per-level` growth; CRT/CRT_DMG now stay fixed at `base` regardless of level (`StatusGrowthConfig#isFixed` - only relic/accessory bonuses move them). The default level cap moved from 100 to 80 (the math supports up to 300). Since values can now run much larger, a monster's nametag HP bar formats them as `long` instead of `int`.
- Unified, staggered level-up feedback (`rpg.status.service.LevelUpFeedbackService`) — a character level-up shows a title/sound/particle immediately, then (after `config.yml: status.level-up-effect`'s `chat-delay-ticks`) the "leveled up" chat line, then (after `stat-delay-ticks`) the stats that actually grew - staggered instead of all landing in the same tick, so it reads as one connected moment. An invalid Sound/Particle name is silently skipped. Job/gathering level-ups (`GatheringLevelService`) go through the same service now too, so the feedback is consistent across the board.
- Always-visible experience — the action bar (`config.yml: action-bar.format`'s `{level}`/`{exp_bar}`) now shows the current level and a progress bar toward the next one at all times, drawn with the same "colored strikethrough (`&m`) + spaces" trick as a monster's nametag HP bar (block characters read poorly at the action bar's compact size) - see `ActionBarService#expBar`'s filled/empty color constants. The Status GUI (`/ol status`) head icon's lore shows experience (current/required, or `MAX` at the level cap).
- Extra monster-only growth bonus (`config.yml: monster.target-level-bonus`) — a multiplier layered on top of the shared `stat-scaling.growth-rate`, applying only to a monster spawned with a `targetLevel` (default `HP:1.02`/`ATK:1.015`/`DEF:1.012`, roughly 4.8x/3.2x/2.6x a same-level player by Lv80). Growing at exactly the player-shared rate turned out to leave scaled monsters underwhelmingly weak by max level; a monster with no `targetLevel` is completely unaffected.
- Job-change GUI pagination (`/ol job`) — once job types exceed 7, the rest spill onto a second page via the shared `GuiPaginator`/`GuiPageLayout` framework. Previously the only bounds check was the whole screen's tail slot, so the 8th job type crept into a slot meant to stay empty.
- Monster/boss ability attacks (AOE_SLAM/FIREBALL_BARRAGE) now correctly flow through the scaled-stat pipeline — they used to call the damager-less `player.damage(amount)` directly, so `monsters.yml`/`bosses.yml`'s `damage:` value bypassed DEF mitigation and the scaled-to-vanilla conversion entirely, landing straight on the player's vanilla health. `damage:` is now a multiplier on that monster's/boss's own (level-scaled) attack power and goes through the same DEF/crit/elemental-weakness pipeline as a normal hit.
- Toned down the exaggerated vanilla hurt-flash/heart-shake effect when hitting a monster — `config.yml: combat.scaled-health.vanilla-cap`'s default dropped from 1024 to 20. A monster's health display is driven by its nametag (reading the scaled value directly), so its vanilla MAX_HEALTH attribute is an internal value never shown to players; shrinking it doesn't affect the health bar's accuracy or one-shot-kill detection.
- Removed per-weapon crit multiplier (`items.yml`'s `crit-multiplier` deleted) — a player's crit damage multiplier is now always the fixed base `DamageFormula.DEFAULT_CRIT_MULTIPLIER` (1.5x) plus the `CRT_DMG` stat alone. This was confusing next to the Status GUI's "crit damage" stat with no clear relationship; monster/boss `crit-multiplier` (`monsters.yml`/`bosses.yml`) is unchanged and out of scope here.
- Localized the stat-growth labels shown on level-up — elemental damage stats (fire/water/earth/wind/light/dark) used to show up as raw enum names like `FIRE_DMG`; `LevelUpFeedbackService#STAT_LABELS` now has Japanese labels for all 6.
- Changed the player's default crit rate/crit damage (`config.yml: status.growth.CRT/CRT_DMG.base`) to 10/50 respectively (previously 5/5). Since CRT/CRT_DMG stay fixed regardless of level (see above), this is now literally the character's base 10% crit rate and +50% crit damage.
- Fixed a color gap in the action-bar experience bar — `ActionBarService#expBar` ended on `&r` (a full reset), so the trailing `] 1234/3000` fell back to plain white instead of matching the rest of the HUD line. It now applies the bar's own color constant after the reset too.
- Quest log GUI (`/ol quest gui`) — opens the quest log (`QuestGuiScreen`, now on the shared `GuiPaginator`) without talking to an NPC. Grouped by quest type (MAIN/SUB/DAILY/WEEKLY/EVENT); quests you can't currently accept still show up, greyed out with the lock reason (level too low, prerequisite missing, ...). Ships with 23 default quests (Lv1-40); the quest-unlock notice and `quest.newly-unlocked` quest names are clickable and open this GUI. Several main-line quests play a `dialogues.yml` tree on accept/report (`start-dialogue-id`/`complete-dialogue-id`).
- Guild GUI (`/guild gui`) — `GuildGuiScreen` (also on `GuiPaginator`) lists guilds and member rosters; guild names in messages like `guild.created` are clickable and open it. The list screen shows a "ギルドを作成" button when you're not in one - clicking it pre-fills `/guild create ` into chat, since name+tag are two free-text fields a GUI click alone can't fill in.
- Party GUI (`/party gui`) and Friend GUI (`/friend gui`) — same `GuiPaginator`-based shape as the guild GUI. Party: a "パーティーを作成" button when not in one; otherwise the member roster (leader can shift-click a member to kick), an "招待" button (pre-fills `/party invite `), and a leave/disband button. Friend: the friend list plus a "フレンド追加" button (pre-fills `/friend add `); each entry sends a teleport request on click and removes the friend on shift-click. Every button runs the matching `/party`/`/friend` command rather than calling `PartyService`/`FriendService` directly, so existing side effects (sound notifications, etc.) fire the same as they would from chat.
- Chat mute — `/chat mute <public|party|guild>` mutes only the chat lines you actually type into that channel (public/party/guild - `ChatMuteService`). System-driven notifications (party/guild invites, trade requests, unread-mail notices - both the message and their `config.yml` `notify-sound` blocks) are never affected by this and always come through. `config.yml`'s `chat.mute.enabled` can disable `/chat mute` entirely (ignoring any existing mutes) if it doesn't fit your server.
- Config-browsing command (`/oladmin config <core|world|extra> view <file> [path]`) — renders a config file (e.g. `monsters.yml`, `quests.yml`) as a readable YAML tree instead of raw text; clicking a leaf value auto-fills the edit command in chat (`DebugApi`/`WorldDebugApi`/`ExtraDebugApi`'s `listConfigTree`).
